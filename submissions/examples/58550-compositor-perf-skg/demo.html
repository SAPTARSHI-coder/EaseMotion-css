Compositor-Only Animations

A visual guide to why EaseMotion CSS enforces transform and opacity for all keyframe animations — and how stylelint-high-performance-animation prevents layout-triggering regressions in every PR.

How the Browser Renders a Frame

The browser runs three sequential stages per animation frame. Only the last stage runs on the GPU compositor thread — interrupting earlier stages forces the CPU back into expensive work.

1
Layout
Recalculates geometry of every affected element when width, height, top, margin, or padding changes
🔴 Expensive — CPU, blocks thread
→
2
Paint
Fills in pixels when color, background, border, or box-shadow changes
🟡 Moderate — CPU rasterization
→
3
Composite
Moves and blends already-painted layers using transform and opacity
🟢 Free on GPU — no CPU stall

Live Demo: Jank vs Smooth

Both boxes animate identically on screen — but one forces layout recalculation every frame while the other runs entirely on the GPU compositor.

Paint-Heavy (Bad)

Animates: top, left, width

Triggers: Layout → Paint → Composite every frame

@keyframes bad-move {
  from { top: 0px; left: 0px; width: 60px; }
  to   { top: 40px; left: 40px; width: 90px; }
}
/* ❌ layout-triggering on every frame */

Compositor-Only (Good)

Animates: transform, opacity

Triggers: Composite only — GPU handles it

@keyframes good-move {
  from { transform: translate(0, 0) scale(1); opacity: 1; }
  to   { transform: translate(40px, 40px) scale(1.5); opacity: .7; }
}
/* ✅ compositor-only — zero layout recalc */

Property Reference: Safe vs Unsafe

Use this as a quick lookup when writing or reviewing keyframe animations in EaseMotion CSS.

Property Pipeline cost Use in keyframes? Compositor alternative
transform Composite only ✅ Yes — (this is the alternative)
opacity Composite only ✅ Yes — (this is the alternative)
filter Composite (GPU) ⚠️ With caution Use transform where possible
top / left / bottom / right Layout + Paint ❌ No transform: translate(x, y)
width / height Layout + Paint ❌ No transform: scale()
margin / padding Layout + Paint ❌ No transform: translate()
background-color Paint only ❌ No Fade overlay with opacity
box-shadow Paint only ❌ No Animate opacity on a pseudo-element shadow
border-width Layout + Paint ❌ No outline or box-shadow inset (paint-only)

Refactor Patterns

Common paint-heavy keyframes found in community submissions, and their compositor-only equivalents.

Before — triggers Layout 
@keyframes bounce-old {
  0%   { top: 0; }
  50%  { top: -20px; }
  100% { top: 0; }
}
After — compositor-only 
@keyframes ease-kf-bounce {
  0%   { transform: translateY(0); }
  50%  { transform: translateY(-20px); }
  100% { transform: translateY(0); }
}
Before — triggers Layout + Paint 
@keyframes expand-old {
  from { width: 100px; height: 100px; }
  to   { width: 200px; height: 200px; }
}
After — compositor-only 
@keyframes ease-kf-expand {
  from { transform: scale(1); }
  to   { transform: scale(2); }
}
Before — triggers Paint 
@keyframes shadow-pulse-old {
  0%   { box-shadow: 0 0 0 rgba(59,130,246,0); }
  50%  { box-shadow: 0 0 20px rgba(59,130,246,.6); }
  100% { box-shadow: 0 0 0 rgba(59,130,246,0); }
}
After — opacity on ::after pseudo-element 
/* Static shadow on ::after; animate opacity */
.glow-btn::after {
  content: "";
  box-shadow: 0 0 20px rgba(59,130,246,.6);
  opacity: 0;
  animation: ease-kf-glow-pulse 2s ease infinite;
}
@keyframes ease-kf-glow-pulse {
  0%, 100% { opacity: 0; }
  50%       { opacity: 1; }
}
Before — margin triggers Layout 
@keyframes slide-right-old {
  from { margin-left: -100%; }
  to   { margin-left: 0; }
}
After — compositor-only 
@keyframes ease-kf-slide-in-left {
  from { transform: translate3d(-100%, 0, 0); opacity: 0; }
  to   { transform: translate3d(0, 0, 0); opacity: 1; }
}

Enforcing This with Stylelint

The stylelint-high-performance-animation plugin statically analyses CSS files at build time and rejects any @keyframes block that includes layout or paint-triggering properties. This prevents regressions before they reach main.

1. Add the plugin to devDependencies
# npm
npm install --save-dev \
  stylelint \
  stylelint-high-performance-animation

# package.json devDependencies result:
"stylelint": "^17.12.0",
"stylelint-high-performance-animation": "^1.10.0"
2. Update .stylelintrc.json
{
  "extends": "stylelint-config-standard",
  "plugins": [
    "stylelint-high-performance-animation"
  ],
  "rules": {
    /* Reject non-compositor animation properties */
    "plugin/no-low-performance-animation-properties": [
      true,
      {
        "severity": "error",
        "ignore": "paint-properties"
      }
    ]
    /* ... rest of existing rules ... */
  }
}
3. Add npm script (already exists)
// package.json scripts
{
  "lint:css": "stylelint \"**/*.css\""
}

# Run locally before committing:
npm run lint:css

# EaseMotion already has this in CI
# (.github/workflows/ci.yml → Stylelint step)
4. What the linter catches
/* ❌ This will fail the lint step: */
@keyframes bad {
  from { top: 0; width: 100px; }
  to   { top: 20px; width: 200px; }
}
/* Error: Unexpected low performance animation property: top */
/* Error: Unexpected low performance animation property: width */

/* ✅ This passes: */
@keyframes good {
  from { transform: translateY(0); }
  to   { transform: translateY(20px); }
}

Bonus: Hinting the Compositor with will-change

Even compositor-only animations can skip the GPU promotion step on the first frame. Adding will-change: transform, opacity to the animated element tells the browser to promote the layer before the animation starts, eliminating that first-frame flash.

✅ Correct usage

.ease-fade-in {
  will-change: transform, opacity;
  animation: ease-kf-fade-in .4s ease forwards;
}
/* Browser promotes layer before playback */

⚠️ Overuse warning

/* DON'T apply will-change to everything! */
* { will-change: transform; }
/* Promotes ALL elements → wastes GPU memory */
/* Only use on elements that will animate */
