CSS content-visibility

A pure CSS performance demo showing how content-visibility: auto defers rendering of off-screen sections — dramatically reducing initial paint time, layout work, and memory usage. Zero JavaScript. Open DevTools Performance tab and reload.

What is content-visibility?

content-visibility: auto tells the browser to skip rendering (layout, paint, and hit-testing) for elements that are outside the viewport. The browser only renders them when they're about to become visible — saving massive amounts of rendering time.

Combined with contain-intrinsic-size, it reserves space so the scrollbar doesn't jump as content becomes visible. This is a native CSS optimization — no lazy-loading JavaScript needed.

Section 1 — Introduction

This section uses content-visibility: auto. The browser defers its layout and paint until it scrolls near the viewport. The contain-intrinsic-size property reserves 200px of height so the scrollbar behaves correctly.

Section 2 — How It Works

The CSS engine sizes the element to its contain-intrinsic-size value (here: 200px) and defers all actual layout calculation. As the user scrolls, sections entering the viewport are rendered on-demand.

Section 3 — Performance Impact

Skipping layout and paint for off-screen content dramatically reduces the amount of work the browser does on initial page load. This is measured as reduced Layout, Paint, and Composite times in DevTools.

Section 4 — Browser Support

content-visibility is supported in Chromium 85+, with content-visibility: auto being Baseline since 2022. It's a progressive enhancement — browsers that don't support it simply render everything normally.

Section 5 — Best Practices

Always pair content-visibility: auto with contain-intrinsic-size to prevent scrollbar jank. The intrinsic size should be a rough estimate of the element's rendered height — the browser will adjust it once the element is actually rendered.

Section 6 — Use Cases

Blog posts with many sections, long product listing pages, infinite scroll feeds, and any page with large amounts of below-the-fold content benefits from content-visibility: auto.

Section 7 — Memory Benefits

Beyond rendering speed, content-visibility reduces memory pressure by not keeping off-screen paint layers in GPU memory. This is especially impactful on mobile devices and low-power hardware.

Section 8 — Accessibility

Content hidden with content-visibility is still in the DOM and accessible to screen readers and find-in-page. It's not display: none — the content exists, it's just not rendered until needed.

Section 9 — Sub-grid Benefits

When used on sub-elements of a list or grid, content-visibility: auto on each item can reduce layout passes by 60-80% on large data sets. The browser only lays out visible rows.

Section 10 — Summary

content-visibility: auto is one of the most impactful CSS performance features available today. It requires zero JavaScript, is a progressive enhancement, and can reduce initial render time by 50% or more on content-heavy pages.

Section 17

Normal No optimization

Section 1 — Introduction

This section renders normally — the browser lays out, paints, and composites it on page load regardless of viewport position. All sections compete for initial rendering budget.

Section 2 — How It Works

Without content-visibility, every section on the page goes through the full rendering pipeline immediately. This can cause significant main-thread blocking on content-heavy pages.

Section 3 — Performance Impact

With all sections rendering at once, the initial paint time increases linearly with content volume. Each section triggers layout, style recalculation, paint, and compositing — even if it's far off-screen.

Section 4 — Browser Support

Normal rendering is the default and works in all browsers. This is the baseline — every browser renders every element in the DOM, whether it's visible or not.

Section 5 — Best Practices

When you can't use content-visibility, consider virtual scrolling, pagination, or JavaScript-powered lazy rendering to achieve similar performance gains.

Section 6

Every DOM element participates in the initial layout tree. With 50 sections, that's 50 full layout calculations on page load.

Section 7

Memory usage is higher because all paint layers are created and stored in GPU memory, even for content the user hasn't seen yet.

Section 8

Style recalculation runs on the entire DOM tree. With many sections, this can cause noticeable jank on lower-end devices.

Section 9

Large DOM trees also impact JavaScript performance — querySelector and DOM traversal take longer as the tree grows.

Section 10

The cumulative effect: slower First Contentful Paint, slower Largest Contentful Paint, and a worse user experience on slow connections and devices.

Section 11

Section 12

Section 13

Section 14

JavaScript-based solutions like Intersection Observer + dynamic import add complexity. content-visibility achieves the same result with one CSS property.

Section 15

Even on modern hardware, rendering 50 complex sections adds up. DevTools will show significantly more Layout events in the normal column.

Section 16

The CSS contain property can help isolate layout, but content-visibility goes further by skipping rendering entirely.

Section 17

The key insight: browsers are good at rendering what's visible. Don't make them render what isn't.
