Astro Island Hydration & EaseMotion Class Timing

EaseMotion's CSS-only classes start working the instant the stylesheet loads. Astro's JavaScript, on the other hand, only wakes up once an island finishes hydrating — and depending on which client:* directive you pick, that can happen immediately, after the browser goes idle, once the element scrolls into view, or not at all on the server. This guide explains the gap and how to design around it.

1. What "hydration" actually delays

Astro ships components as static HTML by default. An island only becomes interactive once its JavaScript bundle downloads, parses, and attaches event listeners — that whole process is "hydration." Until it finishes, any behavior driven by onMouseEnter, onClick, or an IntersectionObserver set up inside the component simply isn't running yet, even though the markup and CSS classes are already on the page.

This matters for EaseMotion because the library has two very different kinds of classes:

Class type Driven by Affected by hydration?
Entrance / scroll-in animations applied directly in markup (e.g. a fade-up class on a static card) Pure CSS (@keyframes, transition) No — runs as soon as the CSS is parsed
Hover / focus state classes already in the HTML (:hover, :focus-visible) Pure CSS pseudo-classes No — the browser handles these natively
Class toggles driven by component state (e.g. "add ease-hover-tilt only after JS confirms pointer support") Island JavaScript Yes — waits for hydration to complete
Trigger logic tied to visibility (re-running an entrance class via IntersectionObserver on route change) Island JavaScript Yes — waits for hydration to complete

2. The five hydration directives, in motion terms

Directive Hydrates when… Motion implication
client:load Immediately after the page loads Safest for above-the-fold interactive motion (hover cards, toggles users will touch right away)
client:idle Once the main thread is free (requestIdleCallback) Fine for secondary interactions; there's a short, variable window where JS-driven classes won't respond yet
client:visible When the element enters the viewport Best paired with CSS-only entrance classes — don't rely on this directive to *trigger* the entrance animation itself
client:media When a CSS media query matches Useful for hiding hover-only motion behind (hover: hover) so touch devices never wait on it
client:only Skips server render, hydrates purely on client No SSR markup at all until JS runs — avoid for anything that should be visible/animated on first paint

3. Problematic vs. recommended pattern

A common beginner mistake: putting an EaseMotion entrance class inside an island and waiting for the island's onMount to add it, instead of just shipping the class in the server-rendered markup.

✗ Delayed by hydration 
---
// Card.jsx (Astro Island)
---
<div client:idle>
  <script>
    // class only added after JS runs
    onMount(() => {
      el.classList.add('ease-fade-up');
    });
  </script>
  <div id="card" class="card">...</div>
</div>
✓ Works before hydration 
---
// Card.astro (no island needed
// for the entrance animation)
---
<div class="card ease-fade-up">
  ...
</div>

<!-- Only hydrate the parts that
     need real interactivity -->
<LikeButton client:visible />

The card animates in as soon as the CSS parses, with zero JavaScript. Only the piece that truly needs a listener — the like button — ships as an island, and it uses client:visible so it hydrates right as the user scrolls to it instead of competing with page load.

4. Hover interactions inside an island

Simple :hover states (color change, lift, tilt) don't need JavaScript at all — write them as plain CSS on the element and they work immediately, hydrated or not. Reserve islands for hover effects that need to read component state or fire a side effect. 

<!-- No JS needed — works instantly, even inside an unhydrated island -->
<div class="ease-hover-tilt card">
  <h3>Pricing</h3>
</div>

/* style.css */
.ease-hover-tilt {
  transition: transform 0.25s ease;
}
.ease-hover-tilt:hover {
  transform: rotate(-2deg) translateY(-4px);
}

5. Checklist: choosing a hydration strategy

  • If the motion is purely CSS (entrance, hover, focus), skip the island entirely or ship the class in server-rendered markup — don't gate it behind onMount.
  • If an interaction must work the instant the page loads (e.g. a hero CTA hover), use client:load.
  • If the interaction is below the fold and not time-critical, use client:visible so hydration cost is deferred until it's needed.
  • If a hover effect only makes sense on pointer devices, gate the island with client:media="(hover: hover)" so touch users never pay the hydration cost.
  • Avoid client:only for anything that should be visible or animated on first paint — there is no server-rendered fallback while JS loads.
  • Never wire an EaseMotion entrance class through an island's mount lifecycle if it can be written directly in the markup — the extra hydration step only adds delay.
